## 优先级审查: 顺序正确,但有一处可优化

### 当前顺序: 信任(1) → 可用性(2) → 品质(3) → 品牌(4)
**评估**: 正确。信任漏洞(假声明/假数据)是阻断性的 — 用户看到假数据就不信任产品,后续优化无意义。

### 可优化: 阶段 2.1 (应用 Shell) 应提到阶段 1
**理由**: 阶段 1.3 (trading/dashboard 加 refreshInterval) 和 1.2 (仪表盘数据替换) 都需要改 dashboard 页面。如果阶段 2.1 要重组路由到 `(app)` 组,dashboard 路径会变。先做 Shell 再填充内容,避免改两次。
**建议**: 把 2.1 (Shell 布局) 提到阶段 1 开头,作为地基;1.x 在 Shell 内填充。

## 可行性审查: 4 项需注意

### ✅ 高可行性 (直接可做)
- 1.1 删 WebSocket 声明: 改 2 行文案,5 分钟
- 1.2 仪表盘假数据: 接真实 API 或空态,1 文件
- 3.2 颜色语义: token 改动,机械
- 4.1 about 清理: 删占位,直接

### ⚠️ 中等风险 (需测试)
- **2.1 应用 Shell / `(app)` 路由组重组**: 这改 middleware 认证路径 + 全部认证页路由。Next.js App Router 路由组移动是高风险操作 — 每个页面内的相对链接、`router.push("/dashboard")` 等可能需更新。**建议**: 不移动路由,而是在现有 layout 层加 `<Sidebar>` + `<TopBar>` 组件,通过 layout 包裹。这样零路由变更。
- **3.1 格式化器迁移 (142 处)**: 规模大但机械。**建议**: 分 5 批 (按文件组),每批 build+test 验证,不一次性改。

### ⚠️ 需产品决策 (阻断)
- **1.4 统一数字**: "beef-only" 还是 "108 商品"? 这不是技术决策,是定位决策。**不解决就无法推进 4.x (品牌)**。需用户拍板。
- **4.3 真实社交证明**: 需真实客户/数据,技术无法解决。

### ⚠️ 潜在冲突
- **3.3 仪表盘 KPI 重构** (hero = 实时价格) **依赖后端有实时价格数据**。当前覆盖率仅 36.4%,很多商品无价。如果基准商品也无价,hero 显示什么? **建议**: hero 用"有数据的商品数 + 覆盖率"而非单一价格,直到覆盖率达 60%+。
