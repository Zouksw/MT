## A. ✅ datasets IDOR 修复（安全）

### 根因（Round 20 定位）
`routes/datasets.ts:137` 调 `getDataset(id)` 不带 userId；service `getDataset(id)` 只查存在性，不比 owner → 任何认证用户凭 ID 可读他人 dataset（含 timeseries + owner 邮箱）。同 service 的 update/delete 走 `requireOwnedDataset(id,userId)` 有 ownership，**read 漏了**。

### 修复（surgical）
`services/datasetService.ts:75` `getDataset(id)` → `getDataset(id, userId?: string)`：
- 传 userId 时，"不存在"与"非你所有"都抛 `NotFoundError`（404）——**无存在性泄露**（比 403 更安全：调用者无法区分两态）
- 不传 userId 时保留原 unscoped 行为（内部/admin 跨用户读仍可用）
- 路由 `datasets.ts:137` 传 `req.userId`

### 验证（三层）
**1. 服务级 5 测试**（`__tests__/datasetService.idor.test.ts`）：
- owner 读自己 → 200 ✓
- non-owner 读他人 → NotFoundError ✓（**回退修复后 FAIL，应用后 PASS** —— gen-tests 双向验证）
- non-owner 收 404 非 403（无泄露）✓
- 真缺失 id 也 404（同 shape）✓
- 不传 userId 保留 unscoped（向后兼容）✓

**2. live HTTP 端到端**（真实注册 A+B 两用户）：
```
A 读自己 dataset → HTTP 200 ✓
B 读 A 的 dataset → HTTP 404 ✓（原 200，IDOR 已闭）
B 读真缺失 id   → HTTP 404 ✓（同 shape，无泄露）
```

**3. 全量回归**：后端 469 通过（+5 新测试），1 预存在 live-DB 失败（datasets 空表，无关）。

## B. ✅ inference.ts 信封绕过（范围收窄，诚实处理）

### Round 20 的判断
inference.ts 全部 11 路由用 `res.json({...})` 各自异形，绕过全局 `{success:true,data}` 信封。

### 本轮发现的约束（Iron Law：先查影响再改）
**3 个前端 caller 直接消费裸 shape**，信封化会破它们：
- `ai/predict/page.tsx` 读 `data.prediction?.values`（顶层 prediction 字段）
- `forecasts/create/page.tsx` 读 `result.values`（顶层 values 字段）
- 错误处理读 `error.error`（顶层 error，非 `error.message`）

→ 若改成 `{success:true,data:{...}}`，前端读 `result.values` 得 undefined → **生产前端崩**。

### 决策
**不盲目信封化**（CLAUDE.md Surgical Changes：不破相邻代码）。本轮只做安全子集：
- **删 `inference.ts:64-85` 的死 try/catch**（catch 仅 log+rethrow，与 asyncHandler+errorHandler 重复，双倍日志）
- 保留 `inference.ts:129` 的 try/catch（非死——它把错误收进 per-item results 数组，是正确的 partial-batch-success 模式）

### 信封统一的正确做法（延期，需协调）
应作为独立跨栈任务：backend 改 shape + 同步改 3 个前端 caller + 改错误格式（error.error → error.message）。**不在本轮做，避免范围蔓延。**
