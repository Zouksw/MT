## 1. 🔴 运行时发现：前端生产服务"假活"（webapp-testing 抓到）

### 症状
Playwright 访问任意页面，浏览器控制台报：
```
Refused to execute script from '.../webpack-806a9aa9b07d9d10.js' because its MIME type ('text/html') is not executable
```
所有 `_next/static/chunks/*.js` 返回 **HTTP 400 + text/html**（Next 的 400 错误页）→ JS 被浏览器 MIME 检查拒绝执行 → **前端对真实用户是纯 HTML 壳，无 React hydration、无交互。**

### 根因
Round 17 我跑了 `next build` 重新生成了新内容哈希（`webpack-13d5b094...`），但 **PM2 的 `mt-frontend` 还跑着旧构建清单（2 小时前启动，predates Round 17）**。旧清单引用 `webpack-806a9aa9...`（新磁盘上不存在）→ 400。

### 修复 + 验证
`pm2 restart mt-frontend` → 重载新清单。验证：
```
curl webpack-13d5b094a234f562.js → HTTP 200 | Content-Type: application/javascript ✓
重跑 Playwright：所有页面 status=OK，无 MIME 错误
```
> **运维教训**：每次 `next build` 后必须重启 `mt-frontend`。建议把 build + restart 合进部署脚本，否则生产前端静默降级为 HTML 壳。

## 2. 🟠 运行时发现：CORS host-mismatch（配置缺口）

### 症状（浏览器控制台）
```
Access to fetch at 'http://localhost:8000/api/auth/verify' from origin 'http://127.0.0.1:3000' 
has been blocked by CORS policy
```
web-vitals 上报 + auth/verify 全被浏览器拦。

### 根因
- `lib/api.ts:7` + `utils/auth.ts:11`：`API_BASE = process.env.NEXT_PUBLIC_API_URL || "http://localhost:8000"`
- 环境未设 `NEXT_PUBLIC_API_URL` → 硬编码 localhost:8000
- 浏览器把 `localhost` 与 `127.0.0.1` 视为**不同源** → CORS 拦截
- 20 处页面级硬编码 `http://localhost:8000`（前序审计已记）

### 性质
**配置缺口，非代码 bug。** 生产用 nginx 同源代理可避免；dev/自托管场景必现。影响：web-vitals 静默丢失、verify 调用失败。**不本轮修（依赖部署环境决策）。**

## 4. 🔴 代码 bug：signals.ts:268 错误消息模板未插值（已修）

### 症状（live）
`GET /api/signals/wheat`（README 示例）返回：
```json
{"error":{"message":"Commodity \"${commodityId}\" not found..."}}
```
**字面量 `${commodityId}` 直接暴露给用户**，而非实际传入的 ID。

### 根因
`backend/src/routes/signals.ts:268` 用了转义的 `\${commodityId}`（模板字符串被转义成字面文本），`commodityId` 在作用域内（line 255 解构自 `req.params`）却没插值。

### 修复 + 验证
```diff
- `Commodity "\${commodityId}" not found. Use GET /api/signals/commodities...`
+ `Commodity "${commodityId}" not found. Use GET /api/signals/commodities...`
```
重启 backend 后实测：`Commodity "wheat" not found...` ✓
回归：65/66 集成测试通过（1 个为预存在 datasets 空表失败，无关）。

## 5. 约定审计（scaffold-api / scaffold-component）

### 5.1 后端 — 真实安全/正确性问题（scaffold-api 对齐）

| # | 位置 | 问题 | 严重度 |
|---|---|---|---|
| **IDOR** | `datasets.ts:133-140` `GET /api/datasets/:id` | 调 `getDataset(id)` **不带 userId** → 任何认证用户凭 ID 可读他人 dataset（含 timeseries）。同 service 的 update/delete 走 `requireOwnedDataset(id,userId)`，**read 漏了** | 🔴 安全 |
| **信封绕过** | `inference.ts` 全部 11 个路由 | 0 个用 `success()` 信封，全 `res.json({...})` 各自异形（`{status,timestamp}` / `{results,summary}` / `{anomalies,statistics}`）→ 客户端拿到与全局 `{success:true,data}` 不同的顶层 shape | 🔴 一致性 |
| **错误类错** | `services/apiKeys.ts:210/248/289` | `throw new Error("...access denied")`（plain Error）→ errorHandler 当 500 处理 + 非 prod 泄露"存在但非你所有"。应为 `NotFoundError`（404 + 不泄露存在性） | 🟠 |
| 类型分裂 | `AuthRequest`（optional userId）vs `AuthenticatedRequest`（required） | 6/13 路由用旧的 `AuthRequest`，被迫写 `if(!req.userId) throw` 防御样板。`signals.ts`/`alerts.ts`/`apiKeys.ts` 等受影响 | 🟡 |
| Zod 缺失 | `inference.ts`（全手解析）/ `beef.ts`（全手解析）/ `signals.ts`（9 路由仅 1 用 Zod） | 手 `Number(req.body.x) || default` 绕过 `VALIDATION_ERROR` 映射 + 类型安全 | 🟡 |

### 5.2 前端 — 约定漂移（scaffold-component 对齐）

| 文件 | 问题 |
|---|---|
| `Alert.tsx` / `Tag.tsx` / `Input.tsx` | 无 cva、无 cn()（手拼模板串）、arrow const（scaffold 禁）、无 `*Variants` 导出、无 `data-slot`、硬编码 palette（`bg-blue-50`/`bg-green-50`…） |
| `ProfessionalChart.tsx`（581 行）/ `PredictionChart.tsx`（525 行） | **god component**（数据变换+副作用+嵌套子组件+render 混一起）、`export default`（scaffold 明禁）、21+ hex 硬编码、inline `style={{}}` 绕过 token |
| `cn()` 采用率 | 仅 11 文件用 cn()，38 文件手拼 className（**3 倍漂移**） |
| 一致正面 | `button.tsx`/`select.tsx` 完全合规；`Input.tsx` token 化良好 |

> 结论：项目自己的 scaffold 约定（cva + cn + 函数声明 + data-slot + token）只在 `ui/` 原语层被遵守，业务组件（charts/trading）大面积漂移。
