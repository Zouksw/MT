## R28-1: upsertFactor count 膨胀 bug ✅

### 根因
`upsertFactor` (`helpers.ts:122-155`) 用 `findUnique` 查存在性时只 `select: { id: true }` —
不查 `value`/`unit`,因此**无法判断值是否变化**。每次重抓同一行(值未变)都执行 upsert 并返回
`{updated:1}`。这与 Round 18 修的 `upsertPrice` 是**同一类 bug**,影响所有 factor 源
(FRED / USDA-PSD / SECEX / ABARES / shipping / weather / commodity_prices)。

### 修复
复用 upsertPrice 的 same-value 短路模式:
- `select` 改为 `{ id: true, value: true, unit: true }`
- 若 `Number(existed.value) === data.value && existed.unit === data.unit` → 返回 `{inserted:0, updated:0}` (no-op)

### 回归测试
`backend/src/services/dataIngestion/__tests__/upsertFactor.test.ts` — 4 测试 (真实 PG):
- 首写 `{inserted:1, updated:0}`
- **重写相同值 `{inserted:0, updated:0}` (核心回归)**
- 值变 `{inserted:0, updated:1}`
- unit 变 `{inserted:0, updated:1}`

**双向验证**: 把短路改成 `sameFactor = false` → 核心回归测试 **FAIL** (返回 `{updated:1}`);
恢复 → **PASS**。

## R28-2: 调度日志误标 + runAll 丢弃 rejected ✅

### 根因 (两个独立 bug)

**Bug A — runSourcesAndLog 误标 (server.ts:36,55-58)**
当 `scraperManager.runSource(name)` 抛错时,catch 设 `results[name] = {inserted:0, updated:0}`
(无 `skipped` 标志)。状态分类器把它当"运行了但 0 产出"→ 标 `warning`。
真实含义是**硬失败**(解析错/网络断),应标 `error`。

**Bug B — runAll 丢弃 rejected (scraperManager.ts:47-51)**
`runAll` 用 `Promise.allSettled`,但 summary 循环**只复制 fulfilled 结果**。
rejected 的源从返回的 map 里**完全消失**。这使 `/api/market/sources/refresh-all` 路由的
`if ("error" in result)` 分支(marketData.ts:527)**成为死代码** — 失败源永远不被记录。

旧测试甚至**断言了错误行为**为特性 ("Failed sources are excluded by Promise.allSettled")。

### 修复
**Bug A**: catch 里设 `{inserted:0, updated:0, error: msg}`;分类器新增 `else if (result.error)`
分支 → `status: "error"`。
**Bug B**: summary 循环 else 分支捕获 rejected → `summary[name] = { error: reason }`。
**类型**: `ScraperResult` 新增 `error?: string` 字段。

### 回归测试
`scraperManager.test.ts`:
- 更新旧 "mixed success and failure" 测试: `results.bad` 从 `toBeUndefined()` → `toEqual({error:"bad failed"})`
- 新增 "rejected sources as {error} entries (regression)" 测试

## R28-3: brl_usd 96% MAPE 异常 — 根因确认 (归数据规范化轮次)

### 现象
brl_usd 预测 MAPE = 96%(vs usd_cny 的 0.21%)。预测值 ~0.197 看似合理。

### 根因 (经 DB 实查确认)
**brl_usd 商品下有两个单位冲突的数据源混存**:
- `exchange_rate_api`: 22 行, close = `0.19-0.20` (反向报价: 1 BRL = 0.19 USD)
- `fred`: 7,900 行, close = `0.83-6.20` (正向报价: 1 USD = 5 BRL)

预测在混合数据上训练,predictionLog 的预测值 ~0.197 (exchange_rate_api 主导的旧窗口);
但 `verifyDuePredictions` (mapeTracking.ts:143) 抓 actuals 时**无 source 过滤**,抓到 predictedAt
之后的 fred 数据 (~5.0)。0.197 vs 5.0 → 96% MAPE。

### 影响范围 (实查全库)
**3 个商品**有多源单位冲突 (range ratio >10x):
| 商品 | unit | 源 | 范围 | 倍数 |
|------|------|----|----|------|
| corn_cme | USD/bu | cme (473) vs usda_ams (4.1) | 美分 vs 美元 | 115x |
| natural_gas_cme | USD/MMBtu | fred (1-30) vs cme (3.08) | 历史 spike 混入 | 29x |
| brl_usd | rate | exchange_rate_api (0.19) vs fred (5.0) | 汇率方向 | 32x |

### 处理
**不在本轮修**(单位规范化是 per-commodity 的数据治理,规模 > R28 快速修复)。
归入新轮次 **R28b: 数据单位规范化**(见 ROADMAP 更新)。修复方向:
- corn_cme: cme 美分 → 美元 (÷100) 或拆 slug
- natural_gas_cme: 过滤 fred 历史 spike 或限制窗口
- brl_usd: 统一报价方向 (保留 fred 正向,清 exchange_rate_api 反向)
